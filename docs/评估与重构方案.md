# DSH Web UI 重构 — 现状评估与方案

> 评估对象：正在运行的 DeepSeek Harness Web 界面（http://127.0.0.1:3080）
> 评估方法：对已安装的 @deepseek-ai/dsh-* 客户端插件的编译产物逐一做结构分析（可读 bundle），并实测运行中服务的注册表与路由。
> 结论先行：**现有 UI 是高度插件化的槽位架构，完全可以重构，且不需要改一行官方包代码**——新建一个 UI 插件接管 root 槽位即可整体替换外壳，原布局作为崩溃回退自动保留。

---

## 一、现状评估

### 1. 架构总览

Web 前端由 **38 个浏览器插件**组成（实测自 window.__DSH_BOOT__ 注册表），每个插件是 npm 包，
其 package.json 内声明 `dsh.client = { platform, inject, immediately }` 并通过 `exports["./client"]`
暴露客户端 bundle。服务端在**每次请求**渲染 index.html 时注入注册表：

```json
window.__DSH_BOOT__ = { "rev": "...", "entries": [
  { "id": "@deepseek-ai/dsh-client-ui-layout", "url": "/plugins/@deepseek-ai/dsh-client-ui-layout/client.js?rev=...", "inject": ["@deepseek-ai/dsh-client-runtime", "@deepseek-ai/dsh-client-ui-theme"] }
]}
```

核心机制（都已从源码确认）：

| 机制 | 结论 |
|---|---|
| 槽位系统 | 树形声明；`root` 为唯一渲染入口且**单胜者**：多个插件注册进 root 时，priority 数值最小者渲染（实测 `dsh-client-ui-slots` 的竞选排序） |
| 服务层 | `ctx` 上可注入 `slots / theme / locale / layout / sessions / workspaces / conversation / settingsScope` 等，跨插件可复用 |
| 状态 | `defineStore({init, persist, actions})`，按 root/session 作用域实例化，支持持久化 |
| 主题 | `ctx.theme` 注册/覆盖 token（static→alias→specific 三层），暗色通过 `body[data-ds-dark-theme]` 切换；DOM 全由 token 变量驱动 |
| 样式 | 每插件内联 CSS Modules（`<style data-plugin-css>`），类名 `<hash>_<camelCase>` |
| 渲染 | React 18，`createSlotRenderer()` 是 React 适配层；`ctx.slots.register({name, children, store, inject, locale, priority}, Component)` 注册 UI |

### 2. 现有布局结构

三栏外壳（`dsh-client-ui-layout` 的 AppFrame 注册进 root）：

```
┌─────────────┬──────────────────────────────┬───────────┐
│ sidebar     │ conversation                 │ details   │
│ 280px(可拖) │ 自适应                        │ 0~520px   │
│             │  ├ session.header            │  (默认关) │
│ ├ logo      │  │  ├ breadcrumbs(子代理链)   │           │
│ ├ 新会话    │  │  ├ 视图 tabs               │           │
│ ├ 工作区/   │  │  └ actions                │           │
│ │ 会话列表  │  ├ chat flow (消息/工具卡)    │           │
│ ├ ...       │  ├ composer (输入+工具栏)     │           │
│ └ footer    │  └ 输入 dock (todo/queue)     │           │
│  (设置)     └──────────────────────────────┴───────────┘
└ 拖拽把手 ×2    shell.overlay 层（弹层）
```

槽位地图（重构的主战场）：`root` 声明 4 个子槽（sidebar / conversation / details / shell.overlay），
conversation 包再声明 11+ 子槽（session、header、composer 链、input dock、view、chat.node 键控槽等），
sidebar 包声明 3 个子槽（workspaces / settings / footer.action）。

### 3. 优点（值得保留的资产）

- **服务层干净**：会话/工作区/对话发送/滚动引擎/图片草稿等全部以服务暴露（如 `ctx.conversation.send`、`ctx.sessions.open`、`chatScroll` 锚点翻页），UI 只是薄层——重构 UI 不必重写任何业务逻辑。
- **槽位边界清晰**：每个 UI 块（工具卡片、todo dock、队列 dock、许可面板、详情面板、设置页等）都是独立注册者，可单独替换。
- **主题系统正规**：三层 token + 亮/暗/系统三态，新主题只需覆盖 CSS 变量。
- **交互细节已打磨**：IME 组合输入、图片拖放/粘贴、锚点式"加载更早"、消息自动跟随滚动等。
- **容错设计**：槽位条目崩溃会 abdicate 并由错误边界兜底——替换品崩溃时原布局自动回退。

### 4. 痛点与重构机会（布局 / 信息架构 / 交互）

| # | 痛点 | 重构方向 |
|---|---|---|
| 1 | 侧边栏信息架构单一：工作区+会话一个平铺列表，无分组折叠/拖拽排序/右键操作，搜索藏在列表内 | 双栏导航（图标 rail + 面板）、会话分组、拖拽、右键菜单、顶置搜索框 + Ctrl+K 命令面板 |
| 2 | 无全局会话导航（跨会话快速跳转、最近访问） | 命令面板 + j/k 键盘导航 + 最近会话 |
| 3 | 聊天流无阅读宽度控制，长文本全宽铺满；工具卡片/引用块视觉层级平 | 最大阅读宽度、消息密度分级、卡片化工具视图、锚点目录 |
| 4 | 右侧 details 栏使用率低（仅工具详情） | 升级为"活动面板"：任务/jobs/goals/子代理/工具详情多 tab |
| 5 | 设置页无搜索，插件配置平铺 | 设置搜索 + 分组重排 + 目录锚点 |
| 6 | 键盘体系缺失（除输入框外几乎无快捷键） | 全局快捷键体系（Ctrl+K、j/k、g s 跳设置…） |
| 7 | 动效少：仅侧边栏折叠、toast | 页面级过渡、骨架屏、hover/按压反馈、暗亮切换过渡 |
| 8 | 观感保守：neutral-bluish 灰 + DeepSeek 蓝的"标准聊天工具"气质，品牌个性弱 | 新视觉方向（见方案三选一） |
| 9 | 空状态平淡（Hero 仅文字+logo） | 有质感的工作区空状态、首次引导 |

## 二、重构方案

### 总体思路

新建 **一个 UI 插件包 `@deepseek-ai/dsh-board-ui`**（就放在本目录 board_ui），注册进 root 槽位
（priority 更低，如 -1）**整体接管外壳**；沿用现有槽位名（sidebar / conversation / details / shell.overlay），
让现有的会话、设置、工具卡片等插件自动落入新外壳——**只换骨架，不重写业务**。
原 AppFrame 保留在注册表中，新外壳崩溃时自动回退，风险可控。

### 分阶段实施

**阶段 1 — 骨架与导航（布局/信息架构核心）**
- 新 root 外壳：左侧双栏导航（56px 图标 rail + 可展开面板）、中部会话、右侧活动面板、底部输入区
- rail：工作区 / 会话 / 任务 / 设置 / 主题切换；面板：会话分组 + 拖拽 + 右键菜单 + 顶置搜索
- 全局命令面板（Ctrl+K）：会话、命令、设置、文件一网打尽
- 键盘导航：j/k 会话切换、g s/g w 跳转、Esc 收起
- 视觉基建：新 token 覆盖（ctx.theme.overrideTokens）+ 新字体/间距/圆角体系 + 暗亮双态

**阶段 2 — 会话区与活动面板（信息架构深化）**
- 聊天流：最大阅读宽度 + 信息密度分级 + 消息元信息条（模型/耗时/token）+ 锚点目录
- 活动面板（右栏多 tab）：任务进度 / 后台任务 / 目标 / 子代理 / 工具详情
- 设置重构：搜索 + 分组 + 锚点目录

**阶段 3 — 细节与体验**
- 动效体系（页面过渡、骨架屏、micro-interaction）
- 响应式细化（窄窗、触屏）
- 无障碍审计（对比度、焦点环、ARIA）

### 技术落地路径（已实测确认）

1. board_ui 建包：`package.json` 声明 `dsh.client: { platform: "web", inject: [...依赖...] }` 与 `exports["./client"]`
2. 打包：esbuild 产出一个 `window.__ModuleLoader__.load({id, factory: (require) => {...}})` 格式的 lib/client.js（外部依赖走 module loader 的 require，与现有包格式一致）
3. 挂载：装进 web profile 的 pnpm workspace（`~/.dsh/profiles/web`），并在 `~/.dsh/profiles/web/cordis.patch.yml` 增加一行 insert 注册新插件
4. 生效：**重启 `dsh web` 进程**（会话全部持久化，重启后本对话可继续）——这一步需要你来做，因为我一旦杀掉这个进程，我自己也在里面运行
5. 验证：刷新页面 → 新外壳接管；若白屏，回退机制 + 卸载 patch 行即可恢复原 UI

### 风险与对策

| 风险 | 对策 |
|---|---|
| root 接管后新外壳 bug 导致白屏 | 保留原 AppFrame 注册，崩溃自动 abdicate 回退；另备一键回滚脚本（注释 patch 行） |
| 依赖现有槽位契约（slot 名、inject 协议） | 阶段 1 沿用全部官方槽位名；新槽位仅增量添加 |
| 重启打断当前对话 | 会话持久化于 ~/.dsh/sessions，重启后从历史记录继续；重启时机由你控制 |
| 官方包升级后不兼容 | 插件只在 patch 层叠加，官方包不动；升级后若契约变化，patch 层优先报错可见 |
